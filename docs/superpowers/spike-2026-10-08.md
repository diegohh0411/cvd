## 3. Server and health

Command used (the app should do the same with `-m <path>`, not `-hf`):

```
llama-server -m Clef-Flash-Q4_K_M.gguf --host 127.0.0.1 --port 8089 -b 16384 -ub 16384
```

- `-b`/`-ub` matter. See section 6.
- Startup time: ready in a few seconds from a warm page cache.
- `GET /health` -> `200` `{"status":"ok"}` (`Content-Type: application/json`). Polling it until it returns 200 is enough as the readiness check. (Not tested: the status before the model finishes loading; llama-server normally returns 503 `{"error":{"code":503,"message":"Loading model",...}}` then.)
- `GET /v1/models` identifies a decision model:

```json
{"models":[{"name":"Clef-Flash-Q4_K_M.gguf", "...":"..."}],"object":"list","data":[{"id":"Clef-Flash-Q4_K_M.gguf","aliases":["Clef-Flash-Q4_K_M.gguf"],"tags":[],"object":"model","architecture":{"input_modalities":["text"],"output_modalities":["decisions"]},"created":1791475589,"owned_by":"llamacpp","meta":{"vocab_type":2,"n_vocab":248320,"n_ctx":262144,"n_ctx_train":262144,"n_embd":4096,"n_params":9075566084,"size":6475468816,"ftype":"Q4_K - Medium"}}]}
```

## 4. Endpoint and payload (verbatim)

Endpoint: **`POST /v1/systemone`**, `Content-Type: application/json`, no streaming, no auth. Docs: `tools/server/README.md` at tag `b11507`, section "TypeSafe-compatible System One API".

Request fields:

- `state`: string, object or array (non-strings are given to the model as JSON text).
- `questions`: non-empty object mapping question id (any string) -> question.
- Question: `type` (`noul` | `choice` | `score`), `instructions` (string/object/array), `criteria`:
  - `noul`: optional (`{"true": "...", "false": "..."}` descriptions).
  - `choice`: object `option -> description|null`.
  - `score`: array of **2 to 10** level descriptions, lowest first.
- `files`/`images`: optional, ignored by this MVP.

Response: `{"model": <string>, "answers": {<qid>: {...}}, "usage": {"input_tokens": n, "output_tokens": 0}}`. Answer fields per type: `noul` -> `noul` (P(true)); `choice` -> `choice`, `probabilities` (object), `confidence`; `score` -> `score` (expected level index, float), `legend` (object of string index -> text), `probabilities` (object of string index -> p), `confidence`. Every answer also has `"type"`. Note: the response `model` is the GGUF filename, and `choice` `probabilities` keys come back in alphabetical order, not request order.

Clef decides all questions of a request **jointly in one prompt** (the README says so), so scores for the same entry differ slightly between a single-question call and a batched call (see section 5).

## 5. Quality and latency on synthetic data

Setup: 3 synthetic JDs (Rust backend, Angular frontend, ML platform) x 10 synthetic CV entries (the full text is in the appendix). Two modes, both with the 0-4 score rubric above:

- **per-call**: one request per (JD, entry), `state = {job_description, cv_entry}`, one question.
- **batched**: one request per JD, `state = <JD string>`, 10 questions (one per entry, entry text inside `instructions`), instruction `"How relevant is this CV entry to the job description? Entry: <text>"`.

Scores (0-4, higher is more relevant), per-call / batched:

| Entry | JD1 Rust backend | JD2 Angular frontend | JD3 ML platform |
|---|---|---|---|
| e1 Rust ledger (backend) | **3.62** / 3.67 | 0.55 / 0.18 | 2.05 / 1.46 |
| e2 Angular dashboard | 0.55 / 0.22 | **3.62** / 3.65 | 0.80 / 0.39 |
| e3 Python/Airflow pipelines | 1.54 / 1.21 | 0.57 / 0.35 | **3.39** / 3.43 |
| e4 Model server project | 2.35 / 1.72 | 0.82 / 0.31 | **3.50** / 3.72 |
| e5 Rust CLI project | 2.20 / 1.90 | 0.57 / 0.18 | 0.90 / 0.56 |
| e6 Angular component library | 1.24 / 0.16 | **3.44** / 3.61 | 0.86 / 0.16 |
| e7 Barista (irrelevant) | 0.31 / 0.11 | 0.28 / 0.09 | 0.45 / 0.07 |
| e8 Sysadmin | 1.53 / 1.60 | 0.50 / 0.33 | 1.90 / 1.74 |
| e9 CS degree | 1.67 / 2.62 | 1.40 / 1.76 | 2.51 / 2.43 |
| e10 iOS app | 0.68 / 0.34 | 0.98 / 0.47 | 0.77 / 0.18 |

Observations (synthetic data, so indicative only):

- The ranking is sensible in both modes: the matching entries are top for each JD, the barista entry is last, the unrelated stack entries are low. A mid-level result for the degree entry (2.4-2.6 on JD1/JD3 batched) shows it values "distributed systems / ML coursework".
- Batched mode separates better (irrelevant entries get lower scores, 0.1-0.4) and is deterministic: repeating the same request returned identical numbers.
- Batched scores for the same entry differ from per-call by 0.0-1.0 (the joint-decision effect), so the matcher should use one consistent mode per ranking, never mix.
- Latency, M-series Mac, Metal, Q4_K_M, batch 4096+:
  - per-call, ~300 input tokens: **0.47-0.62 s** steady state (the first calls and a few outliers took 0.3-3.6 s while the Metal pipelines warmed; the first call of a fresh server was ~0.75 s). Mean 0.49 / 0.54 / 0.56 s for JD1/JD2/JD3.
  - batched, 10 score questions (~1,910-1,920 input tokens): **3.3-3.5 s** per JD (3.37, 3.34, 3.45).
  - 128 `noul` questions with a short instruction each, JD as state (10,924 input tokens, `-ub 16384`): **20.4 s and 22.1 s** (identical output on both runs).
  - Cost is ~linear in input tokens (~0.5 ms per token, roughly 520 tokens/s prompt processing). Each `noul` question costs about 80 tokens even with a 7-word instruction, each score question about 190 tokens with this 5-level legend.
- Estimate for a real match: 128 questions at once is possible but takes ~20 s; the app should show progress. Splitting into several smaller requests is probably better (cancel, progress), but the per-request scores are then not strictly comparable. Decide in Task 7.

## 6. Context limit (the "oversized state" error)

Clef evaluates the **whole prompt (state + all questions) in a single physical batch**, so the effective limit is `--ubatch-size`, not the 262144 context. `llama-server` logs `embeddings enabled: setting n_batch = n_ubatch = 512` for this model, so with default flags **the limit is 512 tokens** per request. A single 300-token pair fits; 10 batched score questions (1,921 tokens) do not.

Overflow response (default flags, `-ub 512`), HTTP **500**:

```json
{"error":{"code":500,"message":"input (1921 tokens) is too large to process. increase the physical batch size (current batch size: 512)","type":"server_error"}}
```

Same error with `-b 4096 -ub 4096` and a 5,145-token state (returned in 0.01 s):

```json
{"error":{"code":500,"message":"input (5145 tokens) is too large to process. increase the physical batch size (current batch size: 4096)","type":"server_error"}}
```

And with 128 noul questions (10,924 tokens) at `-ub 4096`:

```json
{"error":{"code":500,"message":"input (10924 tokens) is too large to process. increase the physical batch size (current batch size: 4096)","type":"server_error"}}
```

The same request succeeded (200, ~21 s) at `-b 16384 -ub 16384`.

Consequences for later tasks:

1. The sidecar **must** be launched with `-b N -ub N` (we recommend `-b 16384 -ub 16384`, which worked on 36 GB; memory use of a large ubatch was not measured, check RAM on 16 GB machines, 8192 may be a safer default). It is not an `-c` problem; `-c` is irrelevant.
2. Overflow is reported as **HTTP 500 with a `message` that starts `input (N tokens) is too large to process`** (not 400 and not 413). The engine should detect it by parsing `^input \((\d+) tokens\) is too large`, and then split the request (fewer questions per call) or truncate the state. The reported N is the exact token count, useful for sizing the retry.
3. Rough budget at `-ub 16384`: JD of ~400 tokens + 128 noul questions fits (10.9k). Long JDs (e.g. 3k tokens) leave room for ~150 score questions only if entries stay out of the state.
4. A pre-flight token estimate of ~4 chars per token is reasonable (the lorem ipsum probe gave ~5.1 tokens per repeated 5-word chunk; the CV text ~4 chars/token).

## 7. Decision

- **Go.** The decision-model path works end to end on macOS arm64 with a published `llama-server` binary and a published GGUF. No conversion needed.
- **Default model:** Clef-Flash `ggml-org/Clef-Flash-GGUF` / `Clef-Flash-Q4_K_M.gguf` (6.5 GB, SHA256 above). Optional: Clef 27B `ggml-org/Clef-GGUF` / `Clef-Q4_K_M.gguf` (19.2 GB). Fallback: Kev-4B `ggml-org/Kev-4B-GGUF` / `Kev-4B-Q4_K_M.gguf` (3.0 GB; unverified quality).
- **llama.cpp pin:** `b11507` (`llama-b11507-bin-macos-arm64.tar.gz`; bundle the dylibs).
- **Endpoint/payload:** `POST /v1/systemone` with `{state, questions:{id:{type, instructions, criteria}}}` and `answers` as in section 4. For relevance use `score` with exactly 5 levels (0-4).
- **Launch flags:** `llama-server -m <gguf> --host 127.0.0.1 --port <free port> -b 16384 -ub 16384`.
- **Differences from the plan's Task 4 assumptions to check:** the brief's shapes are `state` + `questions` of types `noul`/`choice`/`score`; these match what exists. Notable specifics Task 4's serde types must reflect:
  - `questions` is an **object keyed by id**, not an array.
  - `score` criteria is an **array** (2-10 items), `choice` criteria is an **object** (option -> description or null), `noul` criteria is optional.
  - `score` answer `legend`/`probabilities` are objects with **string keys** `"0"`..`"4"`; `choice` probabilities keyed by option name.
  - Answers carry a `type` field; `usage` is `{input_tokens, output_tokens}`; the response also has `model`.
  - Overflow is HTTP 500 (not 400/413).
- Re-run Step 4 with the user's real JDs and entries before shipping, and measure memory at the chosen `-ub`.
